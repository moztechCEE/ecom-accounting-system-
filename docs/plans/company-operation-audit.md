# 營運操作日誌整合方案

2026-09-23。本文件是分階段設計；現有頁面不代表已涵蓋全部 ERP 操作。

## 入口與權限

ERP「系統管理 → 操作日誌」應成為公司的查核入口。查詢條件：公司、来源系統、模組、同仁、時間、動作、結果、單據。儲運工作台不放全員日誌。一般同仁的個人刷錯分析與主管查核日誌分開授權；能執行作業，不代表能讀取別人的日誌。

第一階段保留 WMS 的儲運日誌頁面，由 ERP 單次票證帶入身分；後端重新核對 ERP 權限。`wms_logs:read` 只允許日誌 GET，不能修改訂單、設定或帳號。ERP ADMIN 依既有管理員規則可查詢。未授權員工直接呼叫 API 也應被拒絕。正式中央日誌需新增獨立 `audit_logs:read`、`audit_logs:export` 和公司範圍，預設只授權最高管理員／指定稽核主管，不繼承一般報表或人事主管權限。

## 要記錄什麼

| 來源 | 必要事件 | 業務關聯 |
| --- | --- | --- |
| 帳號與權限 | 登入成功／失敗、權限拒絕、角色和公司授權、帳號停用、2FA 設定、敏感資料查閱或匯出 | 使用者、角色、公司 |
| WMS | 訂單匯入、認領、切換作業、揀貨／裝箱核對、刷錯、完成、例外處理、作廢、放行、物流設定 | 原始訂單、明細、SN、箱號、匯入批次、WMS 任務 |
| 庫存與 SN | 配號、追加、補印、裝箱、調整庫存 | 產品、批次、SN 區間、箱號 |
| 費用／會計 | 申請、主管審核、退回、憑證更換、付款、過帳、沖銷、對帳 | 申請、憑證、分錄、收付款、來源交易 |
| 人事 | 打卡更正、請假核准、薪資調整 | 員工、申請、薪資期間 |

這是待覆蓋的事件清單，不是目前全數已有紀錄。人事薪資和會計需另外套用敏感模組範圍；不把薪資全文開放給所有日誌讀者。

## 統一事件格式與可靠性

每筆包含：全域事件 ID、來源系統、來源事件 ID、schema version、公司、事件時間、收到時間、ERP 使用者 ID、來源使用者 ID、操作者名稱及當時角色快照、動作、結果（成功／失敗／拒絕）、資源種類與 ID、單據參照、request/correlation ID、必要的前後變更白名單、原因和安全的錯誤代碼。

不保存密碼、JWT、SSO 票證、2FA 種子、完整銀行或個資欄位。欄位變更採白名單和遮罩，避免任意 request body 落入日誌。

成功的業務變更與原始稽核事件放在同一資料庫交易。跨系統用 transaction outbox；中央收集端以 `(source, source_event_id)` 唯一鍵去重，保留 checkpoint、重試與延遲告警。不可因中央服務暫停而漏掉已成功操作。失敗或拒絕事件在業務 rollback 後獨立寫入，清楚區分「嘗試」與「成功」。前端提示及一般 Cloud Run 診斷文字不當作唯一稽核證據。

事件採追加方式保存。更正另寫更正事件並關聯原始事件；業務 API 不提供任意刪改日誌。查閱及匯出本身也記錄。保留期間和封存方式需由公司決定，再設定排程及存取權限，不在此擅訂期限。

## 本次實作與限制

- WMS 所有已列出的 ERP 入口使用相同票證流程，目的頁面由 ERP 伺服器決定，不以瀏覽器傳入的角色／URL 授權。
- WMS 日誌不再向一般 socket 廣播人名、客戶或 details；頁面從受權限保護的 API 查詢。
- 新 operation_logs 寫入時由資料庫快照當時的 ERP／WMS 身分與角色；涵蓋既有直接 INSERT 呼叫，交易 rollback 也不留成功紀錄。
- 歷史紀錄不回填猜測角色。舊姓名只可作為目前帳號參照；頁面標示缺少歷史快照。
- 目前 WMS 日誌仍以既有作業事件為主。ERP AuditLogService 只覆蓋部分模組；尚未建置中央事件表、outbox、集中查詢、所有模組事件和匯出審計。

## 後續交付順序與驗收

1. 統一登入及 WMS 修補先在 DEV 驗：管理員直達設定／日誌；倉儲人員不能查日誌；查詢角色不能寫入；帳號停用或權限撤除即失效；SSO 過期回 ERP，無 WMS 密碼表單。
2. 中央事件 schema、outbox、只读 API 和 ERP 日誌頁面。先接 WMS 與 ERP 帳號權限／費用，逐一列出事件覆蓋率。
3. 補庫存、SN、會計、人事與外部同步。驗證同一單據跨系統串接、重試不重複、失敗不冒充成功、跨公司及敏感模組被拒絕。
4. 權限撤除、操作者改名／換角色／停用、訂單作廢後歷史仍可查；斷線重送不漏不重複；同一交易失敗不殘留成功事件。完成 DEV 人員驗收再討論正式環境。
